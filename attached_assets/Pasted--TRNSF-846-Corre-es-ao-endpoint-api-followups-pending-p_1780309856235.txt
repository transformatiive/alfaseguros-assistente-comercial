# TRNSF-846 — Correções ao endpoint `/api/followups/pending` (pós-teste ao vivo)

## Problema 1 — `agent_email` vem `null` em 100% dos casos (BLOQUEADOR)

Nas 200 promessas devolvidas, **todas** trazem `agent_email: null`. O n8n precisa do email para encontrar o agente no Zoho Desk e atribuir-lhe a tarefa. Sem isto, todas as tarefas ficam sem dono — não dá para ativar.

A causa provável: o `AGENT_EMAIL_MAP` está vazio, mal formado, ou a chave usada para o lookup não corresponde ao identificador de agente que existe na conversa.

### O que é preciso

O `AGENT_EMAIL_MAP` mapeia **o ID de agente que o Supervisor tem na conversa** (o ID interno do Ringover/Supervisor, ex.: `"23275677"`) → **o email do agente no Desk**.

**Eu (n8n side) só conheço metade do mapa: os emails de destino válidos no Desk.** A outra metade — que ID interno do Supervisor corresponde a cada pessoa — só o Supervisor sabe. Por isso preciso que do lado do Replit se faça a correspondência.

(Campo novo, opcional, não quebra o contrato.)

## Problema 2 — backlog histórico inteiro a ser devolvido (BLOQUEADOR para arranque)

As 200 promessas vão de **5 a 26 de maio** — é todo o histórico acumulado, não "o que está pendente agora". 198 das 200 têm mais de uma semana. Se o n8n ativar contra isto, cria centenas de tarefas atrasadas, muitas já tratadas offline.

### Decisão de negócio (do Nuno): **ignorar o histórico — só promessas a partir de hoje (1 Jun 2026).**

### Ação — adicionar filtro de data ao `GET /pending`

- Aceitar query param **`since`** (ISO 8601). Quando presente, devolver só promessas com `detected_at >= since`.
- O n8n passará `?since=2026-06-01T00:00:00Z` no arranque, e depois manterá uma janela móvel.
- **Importante para o arranque:** para o histórico antigo não voltar a aparecer eternamente, o ideal é marcá-lo como já-tratado. Duas opções (à tua escolha):
  - (a) endpoint admin one-shot que insere acks "sintéticos" para tudo antes de `2026-06-01` (sem criar tarefas), ou
  - (b) simplesmente confiar no `since` — o n8n nunca pede o histórico, e ele fica adormecido na BD.
- A opção (b) é mais simples e suficiente, desde que o `since` seja respeitado rigorosamente. Preferir (b) salvo objeção.

---

## Problema 3 — `count` preso em 200 (sinal de limite implícito)

A resposta devolveu exatamente 200 e `count: 200`. Cheira a um `LIMIT 200` sem paginação. Pode haver mais promessas escondidas.

### Ação

- Confirmar se há um limite hardcoded. Com o filtro `since` do Problema 2, o volume cai drasticamente (só dias recentes), por isso isto deixa de ser urgente — mas:
- Aceitar query param **`limit`** (default razoável, ex.: 100) e, se o total exceder, suportar **`offset`** ou um cursor. Em alternativa, garantir que com `since` aplicado o resultado nunca é truncado silenciosamente.
- No mínimo, se truncar, indicá-lo (ex.: `"has_more": true`).
