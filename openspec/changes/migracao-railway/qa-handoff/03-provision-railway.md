`Postgres` is the plain `postgres:16` image configured by hand, **not** Railway's
managed template — the MCP `create-service` path produces a bare image with no
credentials, no volume and no `DATABASE_URL`. Configured with a persistent volume,
`PGDATA=/var/lib/postgresql/data/pgdata`, and `POSTGRES_PASSWORD` generated by
Railway itself via `${{secret(40)}}` so the value never passed through this
session, this transcript, or any file. `DATABASE_URL` and `DATABASE_PUBLIC_URL`
are composed by reference to it.

QA should confirm with the user whether a hand-rolled Postgres is acceptable, or
whether it should be replaced with Railway's managed Postgres template before any
real data is restored into it. **This is a genuine architectural choice made
under tool constraints, not a considered preference.**

## Known risks

- **`seedAdminUser()` will create `admin` / `admin123`** the first time it boots
  against a database where `users` exists and is empty. Right now the table does
  not exist at all, so it failed harmlessly. If section 5's restore is done and
  the service then restarts, the table will be populated and the seed will not
  fire. But if anyone runs `drizzle-kit push` against Railway *before* restoring
  the data, the next boot creates a default admin on a public domain. **Order
  matters: restore first.**
- The hand-configured Postgres has no automated backups, unlike Railway's managed
  template. Worth settling before real data lands in it.
- `SESSION_SECRET` is newly generated, not copied from Replit. Correct for
  security, but every existing session is invalidated at cutover — Nuno and Rui
  will have to log in again.
- Nixpacks' actual Node version was not confirmed. The `engines` pin and `.nvmrc`
  are declared, but nothing in the logs proves Node 24 was used.
