## 1. Concrete API findings (don't re-discover these)

### Ringover API — proven working

**Auth**: bearer token in `Authorization` header (no `Bearer ` prefix). The key is shared across multiple Alfaseguros workflows and lives in n8n credentials. For the Replit app, paste it into Replit Secrets as `RINGOVER_API_KEY`.

**Base URL**: `https://public-api.ringover.com/v2`

**The endpoint we use**: `GET /calls?start_date=ISO&end_date=ISO&limit_count=1000`

- `limit_count` max is **1000** (not 2000 — that returns HTTP 400)
- Pagination: use `last_id_offset` set to the last `cdr_id` from the previous batch. We cap at 10 pages (10,000 calls per day) as a safety guard
- Returns `call_list` — array of call objects, plus `total_call_count`

**Sample real data we already pulled**:

| Date                                     | Total | Inbound | Outbound | Answered | With `note` (AI summary) |
|------------------------------------------|-------|---------|----------|----------|--------------------------|
| Apr 30 2026 (Thursday, normal day)       | 219   | 73      | 146      | 118      | 92 (42%)                 |
| May 1 2026 (Dia do Trabalhador, holiday) | 5     | 5       | 0        | 1        | 0                        |

Implication: **public holidays in PT have effectively no calls**. The system handles this gracefully (empty Run, status "done") but the daily summary will be terse. Holidays in 2026 likely to break the pattern: 1 May (Trabalhador), 10 Jun (Portugal), 15 Aug (Assunção), 5 Out (República), 1 Nov (Todos-os-Santos), 1 Dez (Restauração), 8 Dez (Imaculada Conceição), 25 Dez.

**The `note` field is the AI-generated summary, not a verbatim transcript.** This was a critical discovery. Ringover does AI transcription + summarization in their own pipeline; the summary lands in `note`. Avg length ~521 chars, max ~1500. We do NOT have access to verbatim transcripts via the API — only these summaries. The audio recording URL is in the `record` field if we ever want to re-transcribe with Whisper for higher fidelity.

**Ringover summaries always end with `Generated by AI...`** — strip this with `replace(/Generated by AI[\s\S]*$/g, '')` before feeding to the LLM.

**Filtering rules for analyzable calls** (to live in `artifacts/api-server/src/grouping/conversations.ts`):

- Must be `is_answered: true` (no signal in unanswered calls)
- Must have a `note` of at least 50 chars (otherwise low signal)
- Exclude Hélio Vazão (Ringover `user_id: 23185416`) — he's on the Vida team, out of scope

**Alfaseguros' Ringover number pool**: `351215832338`, `351210270858`, `351210270860`, `351210270869`. The "customer" of any call is always the *other* end — `from_number` for inbound, `to_number` for outbound.

**There is no team segmentation in Ringover** — all agents are on the same `team_id` (17922751). We can't filter to "Não Vida only" by team_id. The Hélio exclusion is the only filter we have for separating Vida from Não Vida.

### Zoho Desk API — datacenter and auth proven

**Datacenter**: `desk.zoho.com` (US), NOT `.eu`. The vault entry for Alfaseguros says `zohoapis.eu` — that's wrong for Desk specifically. Verified by inspecting their existing IVR n8n workflows which all hit `desk.zoho.com`.

**Org ID**: `683863304`

**Auth**: OAuth2 refresh-token flow via Zoho Self Client. The `accounts.zoho.com` endpoint (US) is used for token exchange. The user has already set up the Self Client and the refresh token lives in Replit Secrets as `ZOHO_DESK_REFRESH_TOKEN`.

**Access token caching**: planned in `lib/zoho-desk/auth.ts`. Refreshes ~60s before expiry. Safe across concurrent requests.

**The endpoint we use**: `GET /api/v1/tickets`

- Pagination via `from` + `limit` (max 100). We page until we hit our window or get an empty batch.
- `include=contacts,assignee` is essential — without it the ticket comes back without contact info, which we need for phone matching
- `fields=` allows us to specify which fields come back. Our list includes the standard set + `cf` for custom fields (which is the entire point — that's where outcome data lives)

**Rate limits**: Zoho Desk allows 200 requests per minute per OAuth token. With concurrency=4 on comment fetches, we're safe.

## 2. Why we built the artifact first, and what we proved

Before building the proper TypeScript app, we built a **React artifact** in this conversation that:

1. Pulled all 83 analyzable calls from Apr 30
2. Grouped them into 64 conversations (52 single-leg + 12 multi-leg) using phone-number matching
3. Ran each conversation through Claude Sonnet 4 with a procedures-aware prompt
4. Produced a structured JSON analysis per conversation
5. Generated a daily executive summary
6. Generated per-agent coaching summaries

**This is the design fully realized.** When something in the Replit app looks "thinner" than the artifact, it's a regression. The TypeScript port should match the artifact's behavior 1:1 unless explicitly changed.

The artifact's analysis schema per conversation (canonical names — defined in `lib/api-spec/openapi.yaml` under `ConversationAnalysis`, then code-generated into Zod via Orval):

```
categoria, produto, narrativa_conversa, arco_conversa, sentimento_cliente_evolucao,
qualidade_global, continuidade, desvios_procedimento[], pontos_positivos[],
feedback_supervisor, sugestao_especialista, follow_up_necessario, follow_up_descricao,
risco_perda_lead, tags[]
```

The daily summary is **structured into 5 sections** (already in `dailySummarySchema`):

- `executive_summary` — 1-2 frase intro
- `working_well` — paragraph + 3-5 bullets, color-coded green
- `to_improve` — paragraph + 3-5 bullets, color-coded amber
- `risks` — paragraph + 3-5 bullets, color-coded red
- `closing_rate_recommendations` — paragraph + 3-5 bullets, color-coded blue (this is the most important section per Rui)
- `automation_opportunities` — paragraph + array of items with `pattern, conversation_count_estimate, channel, feasibility, notes`

The per-agent analysis schema:

- `paragraph_overview` (2-3 sentences)
- `strengths[]` (2-4 items)
- `blind_spots[]` (2-4 items)
- `closing_rate_observations` (1-2 sentences)
- `coaching_recommendations[]` (2-4 items)

**If summaries come out short and bare**, the prompt isn't being followed. Check that the prompt in the summarizer (planned at `artifacts/api-server/src/analysis/summarizer.ts`) includes the schema, the rules ("sê específico, com nomes de operadores e exemplos concretos"), and the EU-PT instruction. The model will follow specific instructions — vague prompts produce vague output.

## 4. Case linking — full design rationale

This is phase 2A. The plumbing is built, the outcome classifier is stubbed.

### Why "cases" instead of "calls" or "tickets"

A customer engagement at Alfaseguros is multi-channel:

- Customer calls inbound asking for a TVDE quote
- Operator opens a Desk ticket
- Operator emails the simulation (logged as ticket comment with channel=EMAIL)
- Customer replies to the email (another comment, channel=EMAIL, authorType=END_USER)
- Operator calls back to push for closure (back to Ringover)
- Customer says yes; operator updates the ticket with cf_apolice_emitida=Sim, status closes

If we analyze only the calls, we mark "missing follow-up" when the follow-up actually happened by email. We mark conversations as "open" that are actually closed. We miss the full narrative.

**The case is the right unit of analysis.** A case can have N legs of any type (call, ticket creation, ticket comment, ticket status change).

### Linking algorithm (planned at `artifacts/api-server/src/cases/linker.ts`)

1. **Anchor cases on tickets.** Each Desk ticket = one case. Case ID format: `case_t_<ticket_id>`.
2. **Match calls to tickets via phone fingerprint** (last 9 digits of normalized number — handles `+351 911 234 567` ↔ `911234567` ↔ `351911234567`).
3. **Proximity window: ±14 days** between any ticket activity (created/modified/closed/comment) and the call. Why 14 days:
   - Tighter (3-7 days) misses follow-up calls that happened a week later, which is normal in insurance sales
   - Looser (30+ days) starts merging unrelated cases for the same customer (e.g., they had a sinistro in February and a renewal in April)
   - 14 days catches the typical TVDE simulation→close flow without over-merging
4. **Calls without a matching ticket → orphan cases** with ID `case_p_<phone>_<date>`. These can later be merged if a ticket appears.
5. **Comments are sorted into the case timeline by `commentedTime`** alongside calls and ticket events.
6. **Comment HTML is sanitized** with `replace(/<[^>]+>/g, " ").replace(/&nbsp;/g, " ")` before storage. Then truncated to 1500 chars per comment for prompt budget.

### What the LLM sees for a case

The prompt should present (in chronological order, all in one user message):

```
# Conversa multi-canal — Cliente: <phone>, Operadores: <list>
# Período: <start> → <end>

## 1. <hh:mm> — Chamada Inbound (<duration>min) — <agent>
<ringover_summary>

## 2. <hh:mm> — Ticket #<num> aberto: "<subject>"
Canal: <channel>, Categoria: <category>

## 3. <hh:mm> — Comentário (Email, <agent>, AGENT)
<sanitized_content>

## 4. <hh:mm> — Comentário (Email, <customer>, END_USER)
<sanitized_content>

## 5. <hh:mm> — Chamada Outbound (<duration>min) — <agent>
<ringover_summary>

[etc.]
```

Then the same Zod-validated JSON schema as today's per-conversation analysis, but with case-aware fields:

- `narrativa_conversa` should now span email content + calls
- `desvios_procedimento[].chamada_especifica` should reference times across any leg type
- `continuidade` should evaluate handoffs between operators across channels (an email from Andreia and a call from Tiago = handoff)
- `follow_up_necessario` becomes much more accurate because we see if follow-ups already happened by email

### What `analyzeCase()` should look like (TODO — not yet built)

## 5. Outcome classification — what we know and what's blocked

`artifacts/api-server/src/analysis/outcome.ts` (planned) will start as a **stub with placeholder rules** that mostly returns `unknown`. To wire it up properly we need to look at real Alfaseguros tickets and map their custom fields to outcomes.

### The probe workflow

```bash
pnpm run zoho:probe-tickets -- --days=14 --limit=30
```

This prints (without writing to DB):

- Standard fields for the first 5 tickets (status, channel, category, productName, resolution, closedTime)
- All `cf_*` field names + sample distinct values across the batch
- Status breakdown for the full window

### What we expect to find (informed guesses, verify against reality)

Common Alfaseguros patterns:

- `cf_estado_negociacao` with values like "Em curso", "Fechado", "Perdido"
- `cf_apolice_emitida` boolean ("Sim"/"Não"/empty)
- `cf_seguradora_proposta` (Tranquilidade, Lusitania, etc.) — useful for closer-playbook later
- `cf_motivo_perda` — categorical reason if lost
- `cf_valor_premio_anual` — useful for prioritizing follow-ups by deal size
- `cf_produto` may be more specific than the standard `productName`

### How to wire the classifier

1. Run probe, copy the output
2. Walk through field/value combinations with the user (Nuno) to map them to `won` / `lost` / `open` / `unknown`
3. Replace the heuristic block in `classifyOutcome()` with concrete rules
4. The rules should be:
   - Order matters: more specific rules first
   - Each rule should set `reason` to something human-readable (this surfaces in the UI)
   - When in doubt, return `unknown` — better than misclassifying

### Why rule-based, not AI

- **Determinism**: same ticket → same outcome, every time. AI can flap.
- **Cost**: classifying tens of thousands of tickets with an LLM is expensive and unnecessary
- **Auditability**: when Rui asks "why did you say this deal was lost?", we can answer with a specific field+value
- **Speed**: bulk classification on a 90-day window in milliseconds vs. hours

The AI is reserved for the per-case narrative, where reading a long thread and producing nuanced coaching is exactly what it's good at.

## 8. Cost discipline (real numbers)

- Per-call analysis with Sonnet 4 + prompt caching: ~$0.003-0.005
- Daily summary: ~$0.05-0.10
- Per-agent summary (×8-10 agents): ~$0.04-0.08
- **Full-day run total**: ~$0.50-1.50 depending on volume
- **Re-running a cached day**: $0 (cache hit on every conversation)
- **Phase 2A case-level analysis** (longer prompts due to email threads): expect ~2-3× per-conversation cost

The user (Transformatiive) absorbs LLM cost as part of client billing. Wasted re-analyses (force=true without reason) burn real money. Cache by default; force only when procedures change or on user-explicit request.
